# Pipeline architecture

One rule everything below follows: **anything that must be identical across
every baseline gets computed once, saved, and only ever read afterward.**
Nothing downstream is allowed to create its own copy.

**Every baseline must follow this design — no exceptions.** A baseline that
creates its own split, its own affinity graph, or its own cluster count,
even "just this once," breaks the comparison between every baseline, not
just itself. If a baseline's own library needs something these stages
already produce, it reads the saved file — it does not call the library's
own version of that step.

## The 5 stages

Commands to run each stage: [`runbook.md`](runbook.md).

```
1. Dataset prep              datasets/scripts/prepare*.py
   raw file -> clean matrix, subset to the committed gene list (datasets/frozen/<dataset>/genes.txt)
                    |
                    v
2. Evaluation setup          evaluation/prepare_eval.py
   committed split (datasets/frozen/<dataset>/split.csv) + affinity_train.npz + affinity_full.npz + cluster_config.json
                    |
                    v
3. Baselines                 baselines/scvi_baseline.py, pca_baseline.py, seacells_baseline.py, (future) harmony_baseline.py, ...
   the methods under test themselves, clustering included (see below)
                    |
                    v
4. Metrics                   evaluation/metrics.py + compute_metrics.py
   generic scoring math, one small adapter per baseline
                    |
                    v
5. Results                   evaluation/build_results.py
   generated tables -> results/<task>/official/tables.md (never hand-edited)
   verdict          -> results/<task>.md        (handwritten, cites the tables)
```

## What each stage owns, reads, and never touches

| Stage | Owns (only writer) | Reads | Must never do |
|---|---|---|---|
| 1. Dataset prep | `datasets/processed/*.h5ad`; `datasets/frozen/<dataset>/genes.txt`/`.json`⁴ | raw downloads | recompute the gene list when a committed one exists (unless `--refresh-frozen`) |
| 2. Evaluation setup | `datasets/frozen/<dataset>/split.csv`/`.json`⁴, `affinity_train/full.npz`, `affinity_config.json`, `cluster_config.json` | stage 1's output | recompute the split when a committed one exists (unless `--refresh-split`) |
| 3. Baselines | its own `embedding.csv`/`assignments.csv`¹, `config.json` | stage 1 + stage 2's output² | create a split, build its own affinity graph, decide its own cluster count, re-normalize data |
| 4. Metrics | `<baseline>/metrics/`³: `metrics_summary.json`, `metrics_per_batch.csv`, `metrics_per_rare_type.csv`, `frequency_dependence.csv`, `frequency_groups.csv`, `rare_groups.csv`, `metrics_config.json` | stage 2 + stage 3's output | know anything method-specific (that's the adapter's job, below) |
| 5. Results | `results/<task>/<version>/`: `tables.md`, `figures/`, `data/*.csv` (generated by `build_results.py`; version = `official` or `whatif_rare-<rule>`); `results/<task>.md` (handwritten verdict) | stage 4's output across every baseline/dataset | compute anything itself, or judge it (no PASS/FAIL) — only collect, line up, and print; any new number goes in stage 4, and the verdict is handwritten |

¹ Embedding **and** cluster labels together, one file — see Clustering below.
² Split and cluster count always; the affinity graph only if that method needs one as input (SEACells does, as its kernel; scVI/Harmony/ComBat/BBKNN don't — they only meet it later, in stage 4, since every baseline's cohesion is scored against it regardless).
³ Full path `runs/<task>/<dataset>/<baseline>/metrics/`, decided in one place (`compute_metrics.metrics_dir_for`), never passed as a flag. A separate subfolder so stage 3 and stage 4 never write the same folder, and re-scoring never touches the baseline's own output.
⁴ Committed to git, not under `runs/`: the code proposes a gene list / split once, the committed file decides from then on (`evaluation/frozen.py`). Stages 2 and 3 stop if the processed file's genes or cells don't match, and every `config.json` records the two files' sha256 under `frozen`. A baseline's embedding and clusters can be committed the same way (`evaluation/frozen_run.py`, `datasets/frozen/<dataset>/baselines/<baseline>/`), so every machine scores the same file.

## Clustering: where it happens, and where its output lands

**Clustering happens inside stage 3, as part of each baseline's own
script — not as a separate stage.** Its output (the cluster label per
cell) is saved in the *same file* as that baseline's embedding
(`embedding.csv`), as an extra column, not a separate file. For scVI
specifically: `scvi_baseline.py` writes one `embedding.csv` with
`latent_0..latent_9` (the embedding) and `cluster_train_run`/
`cluster_full_run` (the cluster labels) side by side, same rows. Anything
reading a baseline's output (stage 4's metrics) reads cluster assignments
from that one file, never a second one.

**Metrics use only `cluster_full_run`** (one clustering of all cells), for
train and test cells alike, with the full affinity graph -- so the
train/test gap reflects whether the model saw the cells, not which of two
clusterings labeled them (see the task file's Revisions). The
`cluster_train_run` column and `affinity_train.npz` are still written but no
longer read by the scVI/PCA metrics.

Every baseline must still land on the **same number of clusters, K**, for
a given dataset — otherwise comparing e.g. purity or cohesion across
baselines isn't fair (more clusters makes purity trivially easier). *How*
each method reaches K differs, since the methods don't all produce the
same kind of output:

- **The number itself (K) is shared data, decided once** — stage 2
  (`prepare_eval.py`) computes `K = n_cells // 75` (both for train-only and
  full cell counts) and saves it in `cluster_config.json`. Every baseline
  reads it with `common.load_cluster_config` — same create-once-read-many
  pattern as the split and the affinity graph.
- **How a baseline reaches K is method-specific code**, living in stage 3:
  - **scVI, Harmony, ComBat** output an embedding only — Leiden runs on a
    neighbor graph built from that embedding. Leiden takes a *resolution*
    parameter, not a cluster count directly, so these sweep a range of
    resolution values, then narrow in between the two that bracket K, and
    keep whichever gets closest to the shared K (`common.sweep_leiden_to_k`
    — shared *code*, one helper, not reimplemented per baseline).
    Clustering reads the **saved** `embedding.csv`, not the model in
    memory (`common.cluster_embedding_file`): the training script calls it
    right after saving, and `evaluation/recluster.py --run-dir <run>` calls
    it alone — so clustering can change without retraining, and both paths
    run identical code. After re-clustering, re-run stage 4 metrics.
  - **BBKNN** outputs a corrected graph directly — Leiden runs straight on
    that graph (no neighbor graph needs building first), same
    `sweep_leiden_to_k` helper.
  - **SEACells** has clustering built into the method itself — it never
    produces an embedding/graph that something else clusters afterward.
    It reads the same K from `cluster_config.json` and passes it straight
    in as its own `n_SEACells` parameter. No sweep, no helper — just reads
    the shared number.

## How a new baseline gets added later

Only two things, nothing else:
1. One new thin adapter file in stage 3 (e.g. `harmony_baseline.py`) — reads
   stages 1+2 (including `cluster_config.json` for its target K), writes its
   own `embedding.csv`.
2. One small adapter function in stage 4's `compute_metrics.py` — reshapes
   that baseline's particular `embedding.csv` into the standard shape
   (`cell_id, batch, true_type, cluster`) the generic metric functions
   already expect.

The metric math, the split, the affinity graph, and the cluster count never
change to accommodate a new baseline.

## Every saved artifact has a config sidecar

`genes.txt` -> `genes.json`. `split.csv` -> `split.json`. `affinity_*.npz` -> `affinity_config.json`.
Cluster count -> `cluster_config.json`. Same pattern every time: the exact
parameters that produced a file live right next to it, so nothing has to be
reconstructed from memory. A consumer that finds a mismatch (wrong seed,
wrong test_size, wrong ratio) errors loudly instead of silently reusing a
stale file.

## Why this matters, concretely

This isn't just tidiness — it already caused a real bug. An early version
of `scvi_baseline.py` discarded train cells' cluster label from the
full-dataset clustering run, because *assignment* metrics on train cells
don't need it. But *cohesion* scoring for a test cell needs to know every
other cell sharing its cluster, including train cells, from that same run.
Mixing "what does this baseline need" with "what might downstream scoring
need" produced a real correctness bug before a single metric was even
written. Keeping creation and consumption in strictly separate stages is
what catches this class of problem before it happens again.
