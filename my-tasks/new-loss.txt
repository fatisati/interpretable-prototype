current state:
1. possible_pairs

Before:
size[p]           = sum over i of assign[i,p]            # soft, fractional
possible_pairs[p] = 0.5 * size * (size - 1),  clamped at min=0

The problem: n(n−1)/2 is the hard-partition formula. It's only valid when membership is 0 or 1. Applied to soft counts it's wrong in two ways:

(a) WRONG VALUE, always.  Measured against brute force: 0.83x too low.
    Example: 4 cells each 25% assigned -> size = 1.0
             formula says  1.0*0.0/2      = 0      "no pairs here"
             truth is      6 * 0.25*0.25  = 0.375

(b) CAN GO NEGATIVE.  size = 0.5 -> 0.5 * (-0.5) / 2 = -0.125
    A count of pairs went negative. Clamped to exactly 0 -> divide-by-zero downstream.

After:
possible_pairs[p] = 0.5 * ( size[p]^2 - sum_i assign[i,p]^2 )
This is the definition Σ_{i<j} assign[i,p]·assign[j,p] in closed form — verified numerically as an exact identity, and it reduces to exactly n(n−1)/2 on hard assignments (checked: 15.0 = 15.0). Always ≥ 0, so no clamp, no zero, no cliff.

2. edges_inside

Before:
A_part = S[head].T @ (w * S[tail])      # over the sampled edge list
A_na   = A_part + A_part.T
edges_inside = 0.5 * A_na.diagonal()    # comment: "A_na double-counts, halve it"

The problem: the halving corrects A_part + A_part.T, but the edge list was already double-counted. EdgeDataset builds it as affinity.tocoo() with no triu, and the affinity is symmetric and stores self-loops. Verified on bk02:

nnz = 4,648,883  =  2 x 2,295,230 (both directions)  +  58,423 (self-loops)
So each undirected edge {i,j} appears as both (i,j) and (j,i), plus every cell contributes (i,i). Tracing:
A_part[p,p]      = 2*true + self_term
A_na.diagonal()  = 4*true + 2*self_term
0.5 * that       = 2*true + self_term       <- measured: 3.21x too high

After:
self_term    = sum over self-loops of aff[i,i] * assign[i,p]^2
edges_inside = 0.25 * ( A_na.diagonal() - 2 * self_term )
Verified exact (ratio to truth = 1.000000).

found a THIRD bug (2026-09-14), while re-checking section 5's fix was actually correct:

the possible_pairs / edges_inside identities themselves (size^2-sumsq)/2 etc are exactly
correct, re-verified on real bk08 affinity data, ratio 1.000000, no issue there.

but when nassoc_size_scale='full' is on (which is the config we actually use), the code
rescales size linearly (size*cell_scale) but rescales sum_i assign^2 QUADRATICALLY
(sumsq*cell_scale**2). sumsq is a sum over cells just like size is -- both should scale
the same way, linearly. size^2 becomes quadratic automatically because it's the SQUARE of
a linearly-scaled thing, that's not a reason to also square-scale sumsq separately.

checked on real numbers (s28nsc bk08, n_total=58423, n_batch=1024, cell_scale=57): a real
rare prototype (3 cells total, true pairs=4.22) with 1 cell landing in a minibatch:
  current code (c^2):  pairs_eff = 0.00   <- collapses to zero again, same bug as before
  fix (c, linear):      pairs_eff = 43.34  <- noisy but never zero

so the c^2 version silently reintroduces the exact divide-by-zero collapse this whole fix
was for, specifically for rare/small prototypes -- which is also exactly where the
coverage gap (14 vs 19 states found, see decisions.md section "Where we stand") lives.

fixed in scproto.py [D7] and defaults.py nassoc_exact comment. NOT yet rerun on modal --
the nassoc_exact H1/H4 numbers (0.839->0.800) were measured WITH this bug present, so
that comparison needs to be redone before trusting it. full writeup: decisions.md section 7.
