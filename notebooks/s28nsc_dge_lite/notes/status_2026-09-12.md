# Where the scProto loss work stands — 2026-09-12

Read this first after a break. Companion docs: `literature/spatial/decisions.md` (why each
loss version was chosen, with references), `CLAUDE.md` §9b/§9c (the standing rules and the
base config). This file is the *state*: what is measured, what is missing, what to do next.

Everything below: dataset `s28nsc` (NSCLC CosMx, 58,423 cells), K=200, single seed.
Headline table: `tables/bk_sweep_full_comparison.csv` (built from saved per-cell labels
only — no training, no GPU).

---

## 1. What the problem was

`L_nassoc`'s diagonal term decides how compact a prototype has to be. Three successive
versions, three different failures:

```
v1 'volume'  diag = edges_inside[p] / volume[p]            target 1
             volume is ADDITIVE under merging -> merging two prototypes never hurts
             -> one blob + a tail of near-empties. dip_p = 0.000, DGE 0.163

v2 'pair'+mse  diag = edges_inside[p] / possible_pairs[p]  target 1, loss (density-1)^2
             possible_pairs = size*(size-1)/2 hits exactly 0 when a prototype's soft
             MINIBATCH size drops below 1 -> density = edges/1e-8 explodes (logged 371-510
             against a target of 1). An EMPTY prototype costs 1, a SMALL one costs ~1e16,
             so the loss PAID the model to kill prototypes. 15/200 survivors on bk02/bk04.

v3 'pair'+cpm, normalizer = sum(possible_pairs)   <- gamma multiplies exactly what you
             divide by, so gamma*sum(pairs)/sum(pairs) is a CONSTANT: zero gradient.
             gamma did nothing. DGE 0.20-0.25.

v4 (current) cpm + nassoc_size_scale='full' + nassoc_cpm_norm='gful' or 'dpar'
             score[p] = edges_inside[p] - gamma * possible_pairs[p]      (Leiden's CPM,
             Traag et al. PRE 84 016114 (2011) -- a SUBTRACTION, never a division, which
             is exactly why Leiden never hits the v2 blow-up)
             divided by an assignment-INDEPENDENT constant, DMoN-style
             (Tsitsulin et al., JMLR 24 (2023), their 1/(2m)).
```

The two bugs were found by printing the term's value and comparing it to its theoretical
range, not by theory. That is now CLAUDE.md §9b, and it is the single most useful rule
here.

## 2. What the current normalizers are

Both are v4; they differ only in the **constant** the CPM sum is divided by.

```
'gful'  denominator = full-graph total edge weight            (DMoN's 2m, published)
        -> term is O(1), portable across datasets/batch sizes, but SMALL, so
           lambda_nassoc must be raised to ~100-1000 or the term is ignored.

'dpar'  denominator = DETACHED sum(possible_pairs)            (ours, from the objective's
        own bounds: score[p] in [-gamma*pairs[p], (1-gamma)*pairs[p]], so dividing the
        sum by sum(pairs) puts the whole term in [-(1-gamma), +gamma] for ANY dataset)
        -> detaching is what keeps gamma's gradient alive (v3's bug was NOT detaching).

'graf'  denominator = summed weight of THIS step's sampled edges. Minibatch-scaled against
        a full-scale numerator -> ~3900x over-weighted (nassoc was 2874 of a 2888 total
        loss). Kept only so older runs reproduce. DO NOT start new runs on it.
```

## 3. What the numbers say (`tables/bk_sweep_full_comparison.csv`)

At BANKSY lambda = 0.2, K=200, DGE pearson_r (recovery of within-cell-type niche fold
changes vs. real single cells):

| arm | lambda_nassoc | DGE r | coverage (pairs/146) | joint pur | ct pur | niche pur |
|---|---|---|---|---|---|---|
| SEACells | - | **0.849 ±0.083** | 19 | 0.504 | 0.823 | 0.591 |
| scProto gful | 1000 | **0.839 ±0.106** | 14 | 0.431 | 0.849 | 0.488 |
| scProto gful | 100 | 0.829 ±0.129 | 13 | 0.429 | 0.846 | 0.488 |
| scProto dpar (g=0.01) | 100 | 0.778 ±0.171 | 16 | 0.439 | 0.861 | 0.494 |
| scProto dpar (g=0.03) | 100 | 0.776 ±0.254 | 13 | 0.439 | 0.858 | 0.495 |
| scProto graf | 1 | 0.760 ±0.197 | 12 | 0.431 | 0.839 | 0.491 |
| scProto gful | 1 | 0.496 ±0.182 | 27 | 0.357 | 0.790 | 0.417 |

**The bk0.2 gap to SEACells is closed** (0.839 vs 0.849, ±0.1) once `gful` is given a
large enough `lambda_nassoc`. The old "scProto 0.76 < SEACells 0.85 at 0.2" statement is
stale — it was the under-weighted `graf` run.

**gful vs dpar at matched lambda=100:** gful 0.829 vs dpar 0.776, and dpar's std is much
wider (0.254). dpar buys slightly higher cell-type purity (0.858 vs 0.846) and joint
purity (0.439 vs 0.429) but loses DGE. On current evidence **gful is the one to carry
forward**; dpar is not dead, it is under-tested (one lambda, one BANKSY value).

**Coverage is the unsolved one.** SEACells tests 19-21 of the 146 (cell type, niche) pairs;
every healthy scProto run tests 11-16. Mechanism is simple: scProto's median metacell is
~292 cells, SEACells' is 208-258, and a pair is only testable when enough metacells are
purely in it. Coverage is therefore a `gamma` (resolution) question, not a normalizer
question — see §5.

**Do not read the collapsed runs' good-looking numbers.** `gful lam1` covers 27 pairs and
scores homogeneity 0.755 — both are artifacts of dumping cells into a few big metacells
(median size 7, `dip_p` = 0.000). Purity and homogeneity pull in opposite directions:
fragmentation inflates purity, collapse inflates homogeneity. Always read them with
`median_size` / `dip_p` / `largest_share` next to them.

## 5. Open question that most likely matters: gamma

`gamma` is the "hole price" — the affinity you are willing to give up per possible pair
inside a prototype, i.e. the resolution knob that sets target metacell size. It was
derived for ~75 cells/metacell; runs land at ~292. Raising gamma should shrink metacells,
which is the direct lever on **coverage**, which is the metric scProto currently loses on
and the one the spatial claim depends on. This has never been swept on a healthy `gful`
run — every gamma value tested so far was on a run where gamma had no gradient (v3) or
the term was under-weighted (graf lam1).
